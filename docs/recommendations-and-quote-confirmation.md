# 推荐接口与买家确认报价

## 推荐 API

`GET /store/recommendations?product_id=prod_xxx&limit=8`

- 需要有效的 `x-publishable-api-key`；商品候选限制在该密钥关联的销售渠道内。
- 已支持 S4 JSON：优先登录用户推荐，其次 product_id 对应相似商品，再用产物 fallback；文件不可用时使用原有分类/新近程度规则推荐。配置与联调见 [S1–S4 对接说明](s1-s4-json-integration.md)。
- `limit` 是 1–24 的整数，默认 8；无效参数返回 400。
- 返回 recommendations、count、limit、source、model_version、strategy、personalized；模型结果带 generated_at，规则降级带 fallback_reason。
- 过滤未发布商品、无变体商品，排除当前商品并去重。未关联当前渠道的参考商品返回 404。
- 模型每个列表最多 200 项，按当前渠道重新核验候选。规则降级最多读取 200 条渠道关联，不代表全目录最优排序。
- 用户身份取自登录认证；customer_id 如传入必须匹配。仅 by_user 命中声明 personalized 为 true，响应禁止共享缓存。
- 商品详情页已接入。展示商品卡前仍使用标准商品 API 获取当前地区价格。推荐 API 不可用时回退到原关联商品展示。
- 保留旧商品图片存储域名的精确白名单（仅 `/media-medusa/**`），避免推荐卡片因历史图片地址触发 Next Image 渲染错误。

## 买家确认报价

`POST /store/custom-orders/:id/confirm`

需要客户 session / bearer 认证。请求体只能包含：

```json
{ "version": 3, "quoted_amount": 680, "currency_code": "cny" }
```

- 从订单详情取得当前 `version`、报价和币种，金额沿用定制订单的最小货币单位约定。
- 仅订单所属买家可确认 `quote → confirmed`；普通 PATCH 仍只允许客户更新 metadata。
- 事务内重新核对归属、状态、版本、报价、币种。报价已经变更时返回 409，刷新后重新确认。
- 更新状态和写入客户身份的状态历史在同一事务完成。事务内读取前先取得订单行写锁并刷新快照；版本号用于拒绝过期报价，不能单独代替数据库原子锁。重复确认不会写入重复历史；已确认订单的再次确认返回拒绝。
- 中英文订单详情页已添加确认按钮。确认报价不扣款，不会把支付状态伪装成成功。

## 独立初始化定制产品分类

在后端目录执行 `pnpm setup:custom-order-category`。这会连接当前配置的数据库并且可能新增一个分类，必须由管理员确认目标环境后运行；本轮仅在隔离测试库验证，未在共享业务库执行。

- 只创建缺失的正式 `Custom Order` 分类，固定 handle 为 `custom-order`，新增时设置 `custom_order_enabled: true`。
- 重跑返回同一个分类，不重跑整库 seed，不创建商品、账号或店铺。
- 兼容按名称找到的旧分类；已有分类不被改名、不覆盖 metadata，也不会自动把停用/内部分类发布出去。
- 名称和 handle 指向不同分类时拒绝操作，要求管理员处理；并发初始化通过唯一 handle 和失败后重查避免重复创建。

## 定制订单支付单准备与查询

`POST /store/custom-orders/:id/payment-collection`，请求体 `{}`；同一路径 `GET` 为只读查询。

- 仅订单所属买家可操作，沿用客户登录和 publishable key 校验。仅已确认且付款标记为 `pending` / `failed` 的订单可准备支付单。
- 金额和币种只能从服务端已确认报价取得。定制报价使用最小单位，Medusa 支付单使用主单位：680 分 CNY 转为 6.8 元；按 Medusa 的币种精度表处理，不对所有币种统一除以 100。
- 绑定存储在订单 metadata 的保留键 `__custom_order_payment_collection_id`。整个 `__custom_order_payment_` 前缀均由服务端管理；客户和管理员不得伪造，替换或清空备注不会删除既有绑定和核验记录。不新增业务字段或数据库迁移。
- 绑定前在事务内取得订单行写锁，重新核对客户、业务状态及版本。重复和并发请求返回同一个持久化绑定；仅清理本次创建而未被采用的空支付单。
- 提交结果不确定时先读持久化绑定，不能确认安全则保留记录并告警，避免误删已绑定支付单；发现支付会话、付款或授权/扣款/退款活动时不自动级联删除。
- 查询核对支付单的订单标记、金额及币种，返回最小摘要，不返回支付机构 payload、敏感 metadata 或客户资料。
- 返回 `verification: "unverified"`。支付单中的状态和金额只是 Medusa 本地账本快照，不是已核验的真实支付结果，不能直接计入收入。
- 支付单准备接口本身不扣款。现已另行实现人民币微信会话、前台支付入口及扣款/退款事件账本核验；只有足额匹配的真实回执可同步为 `captured`。模拟付款不算真实收款。接口、配置和验收边界详见 [定制订单支付说明](custom-order-payments.md)。
- 已关联支付单的订单禁止手工改付款状态、直接取消或删除；生产/交付需重新核验真实账本，不能用管理员手工标记绕过。原有未绑定订单的管理员测试流程仍保留。

## 销售分析

`GET /admin/analytics/sales?from=2026-10-01&to=2026-10-09&currency_code=cny`

- 平台管理员可查看全部或指定店铺；商家只可查看自己店铺。
- `pending` 是 Medusa 普通订单的初始业务状态，不等于支付未完成。收入依据扣款/退款数据判断；草稿和已取消订单排除。
- 收入和热门商品按净收入分摊，多商家订单不得给每家计算整单金额。
- 当前分析对象仍是 Medusa 普通订单，不含独立定制订单；不应把人工维护的定制付款状态直接当成支付账本。

### 定制订单统计

`GET /admin/analytics/custom-orders?from=2026-10-01&to=2026-10-09&currency_code=cny`

- 返回申请总数、进行中/交付/取消数量、每种业务状态和付款标记的数量，以及按申请创建日分组的每日数量。
- 平台管理员可选 `store_id`；商家只能查看自己店铺且有权访问的匠人。平台管理员查看指定店铺时也能包含已分配给其他商家的匠人，不会被错误排除。
- 不返回客户信息，也不把人工维护的付款标记当成真实支付收入。该接口与普通订单销售收入统计分开。
- 默认最近 30 天，最多 366 天。两个分析接口统一采用 UTC 日期；日期形式的 `to` 包含当天至 `23:59:59.999Z`，完整带时区时间戳则保留精确边界。
- 严格拒绝不存在的日期、无时区时间戳、重复筛选参数及跨店铺查询。定制统计最多处理 10000 条，超过时返回 `truncated: true`，不把部分结果伪装成全量结果。

### 当前已核验定制扣款快照

另有只读 `GET /admin/analytics/custom-order-payments`，共用店铺和日期权限，逐笔核对当前支付账本，排除模拟、人工和待复核付款。最多核验 200 个订单，账本不可用或超限明确返回不完整。口径是申请创建日筛选订单后的当前已核验、未退款扣款快照，不是期间现金流或退款净收入；详见 [支付说明](custom-order-payments.md)。原申请数量统计接口保持不变。

### 独立 HTTP 测试

新增 `test:feature:http`，使用显式提供的 `TEST_DATABASE_URL` 所指向的 PostgreSQL 服务器。不会自动使用项目 `DATABASE_URL`。

- 账号需有创建数据库权限；脚本每次产生唯一的 `medusa_feature_test_…` 数据库名，先确认不存在再启动测试。
- 应用启动前再次检查实际数据库名；关闭邮件、Redis、对象存储、Stripe 和 TalkJS 外部调用，微信仅启用本地 mock 并关闭真实定制支付开关；随机生成仅用于测试的登录签名密钥。
- 覆盖真实商品推荐的销售渠道隔离、买家确认与历史记录、过期报价和字段注入、同时确认的并发保护、定制统计和店铺权限，以及分类初始化幂等、并发支付准备/微信会话、支付关联防伪造及模拟扣款不能放行生产。
- 测试结束仅清理本次唯一命名的临时数据库，不清空共享业务库；终端日志遮蔽凭据。新测试采用独立文件后缀，不影响原有 HTTP 测试收集范围。
- 在 PowerShell 中先通过环境变量安全配置独立测试服务器连接，再运行 `pnpm test:feature:http`。不要把连接串、密码或实际 `.env` 提交 GitHub。

## 验证与边界

2026-10-09 本地验证：后端扩展后 36 组、275 项单元测试及 TypeScript 检查通过；12 个独立数据库真实 HTTP 场景通过，包含同时确认只成功一次、分类初始化幂等、并发准备只保留一个支付单/微信会话、禁止伪造关联及越权访问、模拟 capture 事件订阅后仍拒绝生产，以及收款快照权限与只读孤立支付单巡检。前台此前定制支付 12 项、既有购物车/结账/边界/定制申请共 58 项回归及类型检查通过，本轮未改前台。HTTP 中的管理员授权与微信 mock 扣款不代表支付机构实际收款；真实回执正向分支仅用单元样本验证。测试运行器已清理各轮唯一临时数据库。

真实测试发现并修正：通用更新方法的版本 selector 不能单独保证原子并发保护，现改为事务内先取得行写锁并刷新快照；文件模块入口改用当前安装的 `@medusajs/medusa/file`，修复 pnpm/Jest 初始化解析问题。

本轮真实测试另外修正：分类列表查询必须显式选择 `metadata`、可见性等字段，才能正确读回定制标记；策略拒绝的 `NOT_ALLOWED` 在当前 Medusa 映射为 HTTP 400，而客户归属越权为 403，相关测试按真实合同区分。

部署核对：当前公开商品分类接口未查到定制类别，这不足以断言共享数据库中完全没有该类别；需管理员核查分类是否已初始化及是否对外可见。本次未为此重跑整库 seed。

新增测试覆盖推荐排序与参数、渠道查询边界、客户身份、确认报价的版本/金额/币种校验、字段注入，以及销售聚合与店铺权限。

本轮未启动长期本地服务。检查时 8080 前端有监听，9000 后端没有监听；上述 HTTP 验证由隔离测试运行器启动临时后端完成，不能据此认定当前浏览器已能连接到 9000。

本次不新增业务表结构，不自动执行业务 seed，不修改共享库的现有账号或订单，不接入未经配置的外部模型，不自动提交 GitHub。HTTP 验证仅在临时测试库中创建虚拟账号、商品和订单。

2026-10-11 补充：S4 离线模型 JSON 已接入 S1 API，配置与当前联调记录见 [对接说明](s1-s4-json-integration.md)。真实数据产物部署及效果评估、真实商户扫码/退款验收、未付款取消补偿、孤立账本修复和完整定制净收款统计仍需后续完成；生产前全额退款接口的交付边界见 [支付说明](custom-order-payments.md)。
