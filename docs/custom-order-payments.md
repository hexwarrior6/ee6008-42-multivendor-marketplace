# 定制订单微信支付：实现范围与验收

更新日期：2026-10-11。本文描述独立定制订单，不是普通购物车结账。

后续本地修复：创建新支付集合的 POST 接口也检查支付开关、真实支付启用授权、CNY 币种及已启用的微信 provider，不再只依赖前台预检查。已有绑定在支付关闭后仍可只读查询和复用原绑定，不会创建第二个集合。

## 已实现

- 买家确认报价后，人民币订单详情页提供准备支付、查看二维码和刷新支付状态入口，中英文均有说明。
- 服务端先检查微信支付可用性，再准备绑定支付单和支付机构会话；金额、币种、机构和订单归属均由服务端确定，请求体不得传入这些字段。
- 订单行锁串行化会话准备；重复和并发请求复用同一会话。已有付款、多个会话或金额不匹配时拒绝自动创建新尝试，避免重复收款。
- 普通购物车的支付会话接口不能改写定制支付单，必须通过订单所属买家的专用入口操作。
- 订阅 Medusa `payment.captured` / `payment.refunded` 事件，重新读取支付账本后核对状态；买家也可手动刷新。重复事件不会重复更新版本。
- 正常真实回执需匹配微信机构、商户、应用、订单会话、交易号、成功状态、币种及足额扣款。浏览器传入的“成功”、人工支付和 mock 扣款均不能替代这些证据。
- 绑定支付单后，生产/交付推进还会重新检查账本，不能仅信任之前保存的核验标记。发现退款进入人工复核，不自动推进业务状态。
- 增加只读支付巡检和当前已核验收款快照；无效通知时间戳、缺失响应证书序列号及过期响应会被拒绝，微信请求最多等待 10 秒。

## 只读巡检与收款快照

后端执行 `pnpm audit:custom-order-payments` 可报告缺失/重复绑定、报价不匹配、孤立支付单和未结束的内部支付操作。只输出标识与原因码，不输出客户信息、密钥或机构 payload；不联系微信、不删支付单、不改订单。默认最多扫描 10000 个订单和 10000 个支付单，达到限制时显式标记 `truncated`，不把扫描范围以外的引用误判为丢失。本轮仅在隔离测试库验证，未对共享库执行清理。

`GET /admin/analytics/custom-order-payments?from=2026-10-01&to=2026-10-09&currency_code=cny` 共用原定制统计的管理员/店铺隔离及 UTC 日期校验。返回 `verified_capture_amount` 等核验分类数量，不返回单笔客户或支付资料。

- 仅当前足额、匹配的真实微信回执计入已核验扣款；手工 `captured`、mock、未核验及退款待复核记录分别排除并计数。
- 该接口按“申请创建日期”选订单，再读取当前账本，不是期间现金流、结算、退款净收入或完整财务报表；明确返回 `financial_report: false` 和计算口径。
- 同步核验最多 200 个订单、每批最多 10 个账本读取。超限返回 `truncated: true`、`complete: false`；账本不可用或存在待复核记录也不会声称完整。
- 已加入内部持久化操作意图和重复执行保护；管理员生产前全额退款接口见下文。未付款取消、会话重试与孤立账本自动修复尚未公开。

## 管理员生产前全额退款

仅平台管理员可调用 `POST /admin/custom-orders/:id/refund`，请求体只允许 `{"version": 当前订单版本, "reason": "退款原因"}`。客户、卖家不可退款，也不能通过普通 `/admin/payments/:id/refund` 绕过定制订单规则。当前仅接受 confirmed、CNY、单笔足额微信扣款，不允许部分退款或生产/交付后退款。

- 意图先持久化，再在订单行锁内执行。退款编号由订单与支付单生成并冻结；客户端不能指定金额、机构或退款编号。
- 真实模式先查退款；仅验签通过的“退款不存在”响应允许核对原始成功交易并申请全额退款。网络结果不明确时保留原意图，不更换编号。
- `PROCESSING` 返回 HTTP 202，订单保持 confirmed，不提前记账或取消。后续使用相同原因、原请求版本或当前版本再次 POST 恢复，最早一分钟后重新查询；不是后台自动轮询。
- 微信查询确认为 SUCCESS 后才同步 Medusa 退款账本并取消订单。重复/并发恢复不新增退款或取消历史；模拟结果明确标为 `simulated_refund`，不是实际退款到账。
- `GET /admin/custom-orders/:id/refund` 只读返回本地操作摘要，不向微信查单。当前没有专门管理员退款按钮。
- 若微信已成功、但进程在 Medusa 本地退款记录与汇总更新之间中断，账本半写入会拒绝自动继续，必须人工核对；本实现不声称能够自动修复所有崩溃窗口。CLOSED、ABNORMAL、外来退款和金额不一致也需复核。
- 退款完成保留历史付款审计字段；以退款核验状态和账本判断，不把历史 captured 当作净收入。

## 接口

以下接口均需订单所属客户认证及有效 publishable key；所有 POST 请求体为 `{}`。

| 路径（前缀 `/store/custom-orders/:id`） | 用途 |
| --- | --- |
| `GET /payment-session` | 只读检查当前币种和微信机构是否可用；前台在绑定前调用 |
| `POST /payment-collection` | 幂等准备并绑定 Medusa 支付单 |
| `GET /payment-collection` | 返回账本摘要；其 `verification: unverified` 不代表已执行回执核验 |
| `POST /payment-session` | 创建或复用微信会话，只返回必要摘要和支付链接 |
| `POST /payment-status` | 读取账本、核验并同步受保护的定制付款标记 |

报价使用最小单位，Medusa 支付单使用主单位，例如 680 分人民币对应 6.8 元。支付单准备支持 Medusa 币种精度表；当前微信会话和前台支付入口仅支持 CNY，不含定制订单 Stripe 支付。

## 状态与安全边界

- `unverified`：尚无足额、可核验的扣款证据；授权本身不足以允许已绑定订单生产。
- `simulated`：发现 mock / 系统人工支付。前台明确显示模拟提示，不显示可付款二维码，不改为真实已收款。
- `verified`：账本含匹配的真实微信成功回执和足额扣款；服务端可将 `payment_status` 更新为 `captured`，但不会自动标记生产或交付。
- `review_required`：退款、回执不匹配、多次付款等异常需人工核查。退款后保留历史 `captured` 审计标记，但核验状态不再允许生产/交付，不能据此把历史标记当作净收入。

`__custom_order_payment_` 前缀为服务端保留 metadata。创建/普通修改接口拒绝伪造；替换或清空客户备注不删除既有支付关联和核验记录。已绑定订单禁止手工改付款状态、直接取消或删除。未绑定订单的历史管理员模拟流程仍存在，仅供测试，不构成真实收款证据。

支付刷新读取 Medusa 本地账本，不主动向支付机构查单或补扣款；账本尚未更新时仍待核验。微信既有提供器负责验签、解密通知及真实查单，Medusa 支付工作流完成扣款记账后触发本订阅器。通知地址应指向部署后的 `/hooks/payment/wechat_wechat`。

## 配置和真实验收

本轮没有修改实际 `.env`，仅在 `.env.template` 增加默认关闭的：

```dotenv
CUSTOM_ORDER_LIVE_PAYMENTS_ENABLED=false
CUSTOM_ORDER_LIVE_REFUNDS_ENABLED=false
```

本地模拟使用既有 `WECHAT_PAY_ENABLED=true`、`WECHAT_PAY_MODE=mock`、`WECHAT_PAY_SANDBOX=true`。模拟请求不会访问真实微信收款接口。

2026-10-10 已获用户授权实现“生产前已核验微信付款的全额退款”，仅使用模拟测试、真实开关默认关闭。真实退款还需单独启用 `CUSTOM_ORDER_LIVE_REFUNDS_ENABLED=true`，并满足真实定制支付配置；本轮未打开该开关、修改实际 `.env` 或操作真实资金。

启用真实定制支付需要管理员配置完整商户参数、`WECHAT_PAY_MODE=live` 及显式 `CUSTOM_ORDER_LIVE_PAYMENTS_ENABLED=true`，并部署可达的 HTTPS 通知地址。该额外开关不能代替商户参数校验，也不能代替验收。不要将实际密钥提交 GitHub。

仍需完成：

1. 在获准的商户测试环境验证扫码付款、通知验签、真实查单、到账、刷新和生产放行；本轮未操作真实资金，正向真实回执仅由单元测试样本验证。
2. 已实现上述有边界的全额退款接口，但真实商户到账验收尚未进行。未付款取消补偿、会话过期安全重试、部分退款、生产后退款及孤立/半写入账本自动修复不在本轮交付范围。
3. 将定制订单真实净收款纳入财务收入统计；新增已核验扣款快照不等于完整净收款报表。
4. 实际浏览器与部署环境的端到端验收，包括生产事件总线、网络失败和回调重试。本地隔离 HTTP 测试不等于线上验收。
